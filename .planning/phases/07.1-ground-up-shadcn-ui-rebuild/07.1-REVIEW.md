# Phase 07.1 Code Review

## Summary

Reviewed the Phase 07.1 ground-up shadcn UI rebuild at standard depth, including the app shell, shadcn primitives, JSON Analysis rebuild, Live Audio rebuild, design-system components, unit tests, and Playwright coverage.

The implementation generally follows the locked Phase 07.1 decisions: the old bottom-nav/hero frame has been removed, the shadcn Sidebar shell is in place, JSON and Audio surfaces preserve their core behavior, and tests cover the rebuilt UI contracts.

Three actionable warning-level issues were found:

1. Live Audio can show a pronunciation score for a changed reference sentence without a new recording.
2. Mobile Sidebar navigation does not close after selecting an enabled surface.

No critical security issues were found.

## Warnings

### WR-001: Live Audio can rescore an old transcript against a newly edited reference sentence

**File:** `apps/web/components/audio-mode/audio-mode-panel.tsx:95-98,137-145`

**Issue:**  
`pronunciationResult` is recomputed from `transcript.words` and the current `referenceText` whenever `referenceText` changes:

```ts
const pronunciationResult = useMemo<PronunciationResult | null>(() => {
  if (status !== "complete" || transcript.words.length === 0) return null;
  return scorePronunciation(transcript.words, referenceText);
}, [status, transcript.words, referenceText]);
```

After a recording completes, the reference input is editable because it is only disabled during `recording` or `connecting`:

```tsx
disabled={status === "recording" || status === "connecting"}
```

This means a learner can complete one recording, edit the reference sentence, and immediately see a pronunciation result for the old transcript scored against a sentence they did not record. That is a correctness issue in the Live Audio result and can mislead users.

**Fix:**  
Track the reference sentence used for the current attempt, and only score against that locked attempt reference. Clear or hide the completed score when the reference changes after completion.

Add a component test that completes a recording, edits the reference sentence, and asserts the previous `Pronunciation result` is hidden or marked stale until a new recording is made.

### WR-002: Mobile Sidebar remains open after selecting an enabled navigation item

**File:** `apps/web/components/app-shell/app-sidebar.tsx:51-56`

**Issue:**  
Enabled Sidebar items switch surfaces but do not close the mobile Sheet drawer:

```tsx
<SidebarMenuButton
  aria-current={isActive ? "page" : undefined}
  isActive={isActive}
  onClick={() => onSurfaceChange(item.id)}
  tooltip={item.label}
  type="button"
>
```

On mobile, this leaves the drawer overlay open after selecting `JSON Analysis` or `Live Audio Practice`, obscuring the newly selected surface until the learner manually dismisses the drawer with Escape or an outside click. The Phase 07.1 mobile navigation contract requires the shadcn drawer path to be usable as the mobile navigation mechanism; leaving it open after selection is a user-facing navigation regression.

**Fix:**  
Close the mobile Sidebar after enabled surface selection. Since `AppSidebar` is rendered inside `SidebarProvider`, it can use the exported `useSidebar` hook.

Also update the mobile Playwright coverage to assert that after tapping `Live Audio Practice`, the drawer closes and the `Reference sentence` field is visible without requiring an Escape key press.

### WR-003: Coming-soon Sidebar tooltips are not usable when the desktop Sidebar is collapsed

**File:** `apps/web/components/app-shell/app-sidebar.tsx:74-77`; related primitive behavior in `apps/web/components/ui/sidebar.tsx:524-533`

**Issue:**  
Coming-soon items pass `tooltip={item.label}` but also render as native disabled buttons:

```tsx
<SidebarMenuButton
  aria-disabled="true"
  disabled
  tooltip={item.label}
  type="button"
>
```

`SidebarMenuButton` implements tooltips with `TooltipTrigger asChild` around the button. Native disabled buttons do not receive pointer or focus events, so the tooltip cannot open. In collapsed desktop Sidebar state, the visible text is hidden by the icon-only collapsed layout, and the tooltip is the intended way to keep labels readable.

This conflicts with the Phase 07.1 navigation contract that disabled future entries must remain readable in collapsed/tooltip state.

**Fix:**  
Avoid native `disabled` for tooltip-bearing collapsed Sidebar items. Use `aria-disabled`, prevent activation, and preserve disabled styling/accessibility semantics. If retaining native disabled behavior is required, wrap the disabled visual button in a non-disabled tooltip trigger element instead. Update tests from `toBeDisabled()` to explicit non-navigation and disabled-state assertions such as `toHaveAttribute("aria-disabled", "true")`, plus a collapsed Sidebar tooltip/readability assertion.
