# Phase 07.1: Ground-Up Shadcn UI Rebuild — Research

**Researched:** 2026-05-11  
**Domain:** Next.js App Router + shadcn/ui dashboard/app shell rebuild  
**Confidence:** High for repo/package evidence; medium-high for shadcn implementation patterns because they are based on official docs and current repo constraints.

## Summary

Phase 07.1 should be planned as a **ground-up application shell and design-system replacement**, not as another polish pass over Phase 7. The user explicitly rejected the current UI and requested a rebuild from scratch using shadcn/ui, with permission to restructure the UI broadly and stop using the old frame.

The recommended approach is to replace the hand-rolled `app/page.tsx` shell with a shadcn Sidebar-based app shell using `SidebarProvider`, `Sidebar`, `SidebarInset`, `SidebarTrigger`, grouped navigation, and a config-driven surface model. Existing JSON Analysis and Live Audio behavior should be preserved while their visual structure is decomposed into new shadcn-composed feature views.

## User Constraints

- Rebuild the UI from scratch with shadcn/ui; do not reuse the old frame.
- Current UI is rejected as too ugly and must not constrain the new visual architecture.
- It is acceptable to change the whole UI and split/restructure files substantially.
- Preserve JSON analysis behavior: validation, preview, analyze, warnings, result tabs, saved sessions, AI feedback, sample load, clear, and stale-state behavior.
- Preserve live audio behavior: reference text, record button enable/disable, transcript panel, and scoring result.
- Treat Phase 07.1 as urgent work before Phase 8/9 exam-practice surfaces.

## Architecture Patterns

### Pattern 1: Shadcn App Shell

Use the official Sidebar composition:

```text
SidebarProvider
├── AppSidebar
│   └── Sidebar
│       ├── SidebarHeader
│       ├── SidebarContent
│       │   └── SidebarGroup / SidebarMenu / SidebarMenuButton
│       ├── SidebarFooter
│       └── SidebarRail
└── SidebarInset
    ├── AppHeader
    │   ├── SidebarTrigger
    │   └── Breadcrumb
    └── SurfaceRenderer
```

Do not keep `NavItem`, `BottomNavItem`, `QuickStat`, or the old radial-gradient frame in `app/page.tsx`.

### Pattern 2: Config-Driven Navigation

Create a route-ready nav config even if Phase 07.1 keeps client-side surface switching:

```tsx

    id: "ielts-practice",

    enabled: false,

```

Use `SidebarMenuButton isActive` for active states and `tooltip` for collapsed/icon-only states.

### Pattern 3: Keep Behavior Mounted

Preserve current stateful behavior while replacing UI surfaces:

```tsx
<section hidden={activeSurface !== "json"} aria-hidden={activeSurface !== "json"}>
  <JsonAnalysisView />
</section>

<section hidden={activeSurface !== "audio"} aria-hidden={activeSurface !== "audio"}>
  <AudioPracticeView />
</section>
```

This preserves the current “switch without losing state” behavior and avoids duplicate content panels.

### Pattern 4: Product-Level Components Over Primitive Sprawl

Create product-level wrappers that compose shadcn primitives:

- `MetricCard`
- `ActionBanner`
- `StatePanel`
- `EvidenceCard`
- `RecordingControl`
- `PracticeReadinessCard`

These should live outside `components/ui/` so generated shadcn primitives remain clean.

## Don't Hand-Roll

| Problem | Do Not Build | Use Instead |
|---------|--------------|-------------|
| Responsive app shell | Custom desktop rail + fixed bottom nav | shadcn `SidebarProvider`, `Sidebar`, `SidebarInset`, `SidebarTrigger`, `SidebarMenuButton`. |
| Mobile sidebar behavior | Duplicated mobile nav DOM | shadcn Sidebar mobile/offcanvas behavior and Sheet dependency. |
| Tabs keyboard behavior | Custom tab buttons | shadcn `Tabs`, `TabsList`, `TabsTrigger`, `TabsContent`. |
| Card/metric layouts | Ad hoc rounded divs everywhere | shadcn `Card` with `CardHeader`, `CardTitle`, `CardDescription`, `CardAction`, `CardContent`, `CardFooter`. |
| Loading placeholders | Custom gray blocks | shadcn `Skeleton`. |
| Warning/error states | One-off red/yellow cards | shadcn `Alert` plus product `StatePanel`. |
| Input labels | Placeholder-only labels | shadcn `Label` with `htmlFor`, plus existing accessible names. |
| Timers/progress visuals | Custom width bars | shadcn `Progress` plus product timer component. |
| Long result/history scrolling | Overflow hacks | shadcn `ScrollArea`. |

Key principle: hand-rolling navigation and primitive surfaces is how the rejected UI happened. Phase 07.1 should use shadcn primitives for shell, layout, cards, tabs, forms, loading, and status; only product behavior should be custom.

## Common Pitfalls

### Pitfall 1: Treating 07.1 as a polish pass

**Risk:** Tasks tweak colors/radius on the existing frame instead of replacing architecture.  
**Avoidance:** First implementation wave must remove the old custom shell and introduce the shadcn shell.

### Pitfall 2: Duplicate responsive DOM

**Risk:** Playwright strict-mode ambiguity and duplicate labels/IDs.  
**Avoidance:** Use one Sidebar navigation system and one mounted content tree per feature surface. Do not render full desktop and mobile content trees.

### Pitfall 3: Breaking JSON behavior while moving UI

**Risk:** Preview debounce, accepted-for-analysis gate, stale result handling, saved sessions, AI feedback, warnings, or sample load regress.  
**Avoidance:** Extract visual sections around existing behavior first; do not rewrite data flow until tests pass.

### Pitfall 4: Breaking Radix/shadcn accessibility

**Risk:** Tabs lose `tablist`, `tab`, `tabpanel`, or arrow-key navigation.  
**Avoidance:** Keep shadcn/Radix primitive structure intact.

### Pitfall 5: Tailwind token drift

**Risk:** New files accumulate hex literals and one-off visual styles.  
**Avoidance:** Define the product palette in `globals.css`, use semantic tokens, and keep color literals out of feature files except where absolutely justified.

### Pitfall 6: Mobile overflow returns

**Risk:** Dense metrics/tabs/chips exceed 390px width.  
**Avoidance:** Use `min-w-0`, responsive grids, constrained tab lists, and keep Playwright overflow checks.

### Pitfall 7: Placeholder-only inputs

**Risk:** Screen-reader and Playwright label regressions.  
**Avoidance:** Keep accessible labels: `Speech assessment JSON input`, `Reference sentence`, and upload button labels.

## Code Examples

### App Sidebar

```tsx
"use client";

import {
  Sidebar,
  SidebarContent,
  SidebarFooter,
  SidebarGroup,
  SidebarGroupContent,
  SidebarGroupLabel,
  SidebarHeader,
  SidebarMenu,
  SidebarMenuButton,
  SidebarMenuItem,
  SidebarRail,
} from "@/components/ui/sidebar";
import { mainNav, type SurfaceId } from "./nav-config";

export function AppSidebar({
  activeSurface,
  onSurfaceChange,
}: {
  activeSurface: SurfaceId;
  onSurfaceChange: (surface: SurfaceId) => void;
}) {
  return (
    <Sidebar variant="inset" collapsible="icon">
      <SidebarHeader>
        <div className="px-2 py-2">
          <p className="text-base font-semibold">LocalSpeak</p>
          <p className="text-xs text-muted-foreground">IELTS speaking coach</p>
        </div>
      </SidebarHeader>
      <SidebarContent>
        <SidebarGroup>
          <SidebarGroupLabel>Practice</SidebarGroupLabel>
          <SidebarGroupContent>
            <SidebarMenu>
              {mainNav.map((item) => (
                <SidebarMenuItem key={item.id}>
                  <SidebarMenuButton
                    isActive={activeSurface === item.id}
                    disabled={!item.enabled}
                    onClick={() => item.enabled && onSurfaceChange(item.id)}
                    tooltip={item.label}
                  >
                    <item.icon />
                    <span>{item.label}</span>
                  </SidebarMenuButton>
                </SidebarMenuItem>
              ))}
            </SidebarMenu>
          </SidebarGroupContent>
        </SidebarGroup>
      </SidebarContent>
      <SidebarFooter />
      <SidebarRail />
    </Sidebar>
  );
}
```

## Migration Strategy

### Wave 1: Component Inventory and shadcn Additions

- Add missing shadcn primitives: `sidebar`, `sheet`, `scroll-area`, `breadcrumb`, `progress`, `alert`, `label`.
- Confirm existing primitives remain reusable.
- Decide and document design tokens in `globals.css`.
- Do not implement product UI until primitives and tokens are stable.

### Wave 2: Replace App Frame

- Replace `app/page.tsx` custom shell with a thin entry to `LocalSpeakWorkspace`.
- Add `components/app-shell/*`.
- Use `SidebarProvider`, `Sidebar`, `SidebarInset`, `SidebarTrigger`, grouped nav, and route-ready nav config.
- Include disabled/future nav entries for IELTS/TOEIC practice so Phase 8/9 fit the shell.

### Wave 3: JSON Analysis Visual Rebuild

- Preserve existing JSON behavior/API calls.
- Recompose into outcome-first sections:
  - primary next action / practice priority
  - metric cards
  - warnings/state panels
  - evidence tabs
  - saved history
  - secondary JSON input collapsible
- Keep labels and accessible names unless tests are intentionally updated.

### Wave 4: Live Audio Visual Rebuild

- Replace legacy record/transcript class components with shadcn Button/Card/Badge/Progress composition.
- Preserve `referenceText`, session status, transcript, start/stop, and scoring logic.
- Keep record disabled until reference text exists.
- Create a clear speaking flow: prompt/reference, readiness, recording, transcript, result.

### Wave 5: Responsive and Accessibility Hardening

- Rewrite Playwright shell expectations for new shadcn Sidebar DOM.
- Keep phone-width no-overflow checks.
- Keep tab keyboard/role checks.
- Add sidebar trigger/menu focus checks.
- Add empty/error/loading checks for JSON and audio.

## Security Domain

No auth, persistence, provider, or backend changes should be introduced by Phase 07.1.

Preserve:

- Zod parsing for preview/analyze/sample/feedback responses.
- Existing saved-session owner key behavior and tests.
- React text rendering for analyzed words/transcripts; do not introduce `dangerouslySetInnerHTML`.
- Existing server-side provider-key boundary; do not add frontend LLM keys.
