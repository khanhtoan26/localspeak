## Phase 1 UI Scope

Phase 1 UI is a minimal walking-skeleton status page only.

The page must show:

1. Project name: `LocalSpeak`
2. Backend `/health` status
3. `/contracts/sample-json/validate` fixture validation status
4. A manual refresh action
5. Loading, success, and error states for both checks

Do **not** implement:
- Full dashboard
- Auth UI
- JSON input UI
- Audio upload/recording UI
- IELTS analysis tabs
- Charts, score rings, timelines, history, or mode switching
- Shared component library beyond simple local atoms if useful

## Interaction Contract

### Initial Load

On first render:

1. Show page shell immediately.
2. Show both cards in `Checking` state.
3. Fetch same-origin frontend routes:
   - `/api/health`
   - `/api/contracts/sample-json/validate`
4. Update cards independently as each response resolves.

### Refresh

The `Refresh Status` button must:

1. Re-run both checks.
2. Set both cards to `Checking`.
3. Disable itself while both requests are in flight.
4. Restore enabled state when both checks settle.
5. Preserve clear error messages if either request fails.

### API Health Success

If `/api/health` returns success:

- Badge: `OK`
- Title: `API Health`
- Detail copy should include service if available, e.g. `localspeak-api is responding.`
- Metadata may include `status: ok`

### Contract Fixture Success

If `/api/contracts/sample-json/validate` returns `{ valid: true }`:

- Badge: `Valid`
- Title: `Contract Fixture`
- Detail copy should include the contract name if available, e.g. `speech-assessment-response.v1 fixture validates.`
- Metadata may include `issues: 0`

### Error Handling

If either request fails:

- Do not crash the page.
- Keep the other card's result visible if it succeeded.
- Show a concise, actionable message.
- The refresh button remains available after failure.

Required error copy pattern:

```text
Couldn't reach LocalSpeak API. Start the backend with pnpm dev:api or run pnpm dev, then refresh.
```

For invalid fixture:

```text
The sample speech JSON does not match the shared contract. Check packages/contracts and the fixture schema.
```

## Accessibility Contract

| Area | Contract |
|------|----------|
| Semantic structure | Use one `h1`, card headings as `h2` or semantic heading elements |
| Status updates | Status cards should expose readable text; use `aria-live="polite"` for async status result area |
| Button | Native `button`, accessible name `Refresh Status` |
| Color reliance | Badge text must state status; do not rely on color alone |
| Contrast | Dark ink text on warm/white surfaces; muted text only for metadata |
| Keyboard | Refresh button reachable by tab and triggerable by Enter/Space |
| Reduced motion | No required animation; if spinner/pulse is added, keep subtle and nonessential |

## Automated UI Check Contract

Automated checks should verify:

1. The page renders the project name `LocalSpeak`.
2. The page renders API health status when supplied or fetched successfully.
3. The page renders fixture validation status when supplied or fetched successfully.
4. Error state renders actionable copy when backend calls fail.
5. Refresh button exists with accessible label `Refresh Status`.

Minimum expected frontend test assertion examples:

```text
screen.getByText(/localspeak/i)
screen.getByText(/api health/i)
screen.getByText(/contract fixture/i)
screen.getByRole("button", { name: /refresh status/i })
screen.getByText(/api.*ok/i) OR screen.getByText(/responding/i)
screen.getByText(/fixture.*valid/i) OR screen.getByText(/validates/i)
```
